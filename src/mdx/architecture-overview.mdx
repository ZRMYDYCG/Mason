# 架构总览

## 要解决的问题

中后台项目通常都需要登录、菜单、权限、表格、表单、主题、布局、接口封装与基础配置。每次从零搭建成本高。

Mason 提供可复用、可扩展的基础工程，而不是庞大的平台框架。

## 整体分层

- 页面层：业务视图，位于 `views`
- 能力层：组件、Hooks、指令、工具与样式变量
- 应用层：路由、布局、状态、权限、国际化
- 服务层：后端认证、菜单、角色、部门、日志与业务接口

问题按层排查：页面问题看 `views`，权限问题看路由与后端鉴权，样式不一致看 token 与公共组件。

## 前后端协作链路

1. 登录页提交账号、密码和验证码
2. 后端校验后返回用户信息与登录态
3. 前端拉取菜单与权限数据
4. 路由模块按菜单动态注册页面
5. Layout 渲染侧边栏、顶部栏与标签页
6. 业务页面通过 `api` 访问后端

这条链路是主线。新增页面、权限和菜单时，优先保证这条链路不被打乱。

## 路由与菜单

- 静态路由：登录页、错误页、文档页、关于页等不依赖后台菜单的页面
- 动态路由：来自后端菜单，承载管理端业务

公共页面可直接访问；后台页面受登录态与权限控制。

菜单数据包含路径、组件、图标、排序、缓存等字段。前端注册路由与 Layout 渲染共用同一份数据。

## 权限边界

- 前端：控制可见入口与可操作控件
- 后端：控制接口与数据访问

前端权限不能替代后端鉴权。

## 状态流转

全局状态集中在 Pinia：用户信息、菜单、系统设置、主题、语言等。

页面临时状态留在页面内。只有跨页面共享、刷新后仍需保留，或会影响 Layout 的状态，才进入 Store。

## 样式架构

颜色、间距、圆角、阴影、边框等公共规则集中在 token。页面可有局部样式，但不要另起一套视觉体系。

文档、组件、更新日志、关于页复用同一套 Header、Banner、Footer。

## 扩展边界

新增能力时保持：

- 业务页面不吞掉通用逻辑
- 公共组件不绑定具体业务
- 后端接口不把前端展示细节写死
- 权限逻辑不只停留在前端
- 文档与示例随功能更新
